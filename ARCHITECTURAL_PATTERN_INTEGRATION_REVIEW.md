## Executive decision

No P01-P20 proposal justifies enlarging the universal governance kernel with
an application status model, action algebra, resource ledger, graph model,
provider workflow, or distributed-systems mechanism.

The current 3.0.0 implementation is materially stronger than the target
baseline available to the transfer audit. It already implements or validates:

- domain-neutral, restrictions-only extension boundaries;
- separate intended, observed, planned, evidentiary, generated, and historical
  information roles;
- stable typed IDs, version/supersession rules, and per-record lifecycles;
- dependency-derived, non-authorizing readiness;
- typed Git and hosted-operation effects and authority classes;
- exact capability provenance and adoption state;
- approval validity and revocation, coordination fencing, and safe cleanup;
- transactional generation and refresh, rollback-preserving migrations, and
  interrupted-refresh recovery;
- conditional operations, incident, backup/restore, provider-outage, and
  retirement contracts; and
- evidence and readiness claim boundaries backed by adversarial fixtures.

The Project Blueprint-owned disposition is therefore narrower than the source
audit's proposed package set:

1. Preserve the existing kernel without a new universal runtime abstraction.
2. Refine the existing state/projection vocabulary, generation binding
   explanation, evidence claims, and Context Pack contract.
3. Propose a source-only Governed Architecture Pattern Catalog whose records
   are never generated by default and never authorize project adoption.
4. Propose one conditional `architecture-proof` template family.
5. Admit lifecycle disposition and governed change/effect/recovery only as
   reviewed optional patterns. Do not scaffold or implement them until a real
   adopting project supplies the trigger and proof subject.
6. Defer resource accounting, quantitative reservations, bounded
   invalidation, corpus-use machinery, and general policy locks until a
   project demonstrates the corresponding problem.
7. Reject every literal MFMS ontology, topology, status, and workflow transfer.

### PROPOSED-SRC-DEC-A — Govern a source-only Domain-Neutral Architecture Pattern Catalog

- **Status:** proposed.
- **Problem:** Reusable lessons currently live either in canonical Blueprint
  contracts or in source-project material. There is no governed middle layer
  for an optional pattern that is reviewed but not universal or generated.
- **Current behavior:** A mechanism is either described in the Blueprint,
  implemented in a profile/extension, or left project-specific. Promotion and
  rejection rationale are not represented in a catalog lifecycle.
- **Proposed behavior:** Add a source-only catalog outside the kernel and
  generated profile inventories. Catalog records are non-authorizing and never
  generated automatically. Material project adoption still requires a
  project-owned decision where its governance model requires one.
- **Invariant:** A successful local use, template, test, spike, or usage count
  cannot promote a pattern into Blueprint canon or a generated default.
- **Pattern lifecycle:**
  - `candidate` — submitted with source and problem statement; no endorsement;
  - `reviewed` — architecture review and disposition completed; still not a
    recommendation;
  - `experimental` — optional contract is being exercised against an exact
    adopter/proof subject;
  - `recommended` — independently evidenced, compatible, maintained, and
    appropriate for opt-in adoption;
  - `stable` — compatibility and migration support are an explicit Blueprint
    commitment; still not a kernel invariant or default;
  - `deprecated` — retained with reason, successor, compatibility window, and
    migration guidance; and
  - `rejected` — retained with contrary evidence/reason so the proposal is not
    silently reopened.
- **Required pattern record:** Stable ID and version; status; problem;
  invariant; applicability and non-applicability triggers; exclusions;
  required contracts; prohibited shortcuts; failure/recovery semantics; proof
  expectations; known implementations; source projects and exact evidence;
  contrary evidence; compatibility; complexity/operator burden; optional
  assets; successor/deprecation; decision references; limitations; and
  `permission_grant: false`.
- **Alternatives considered:**
  - Put patterns directly in the kernel — rejected as false universality.
  - Store prose-only best practices — rejected because lifecycle, evidence,
    compatibility, and rejection cannot be validated.
  - Do nothing — simpler, but preserves accidental cross-project promotion and
    repeated rediscovery.
- **Compatibility impact:** Additive source-repository capability. No generated
  project changes, profile changes, or kernel version change.
- **Migration impact:** None for generated projects. Existing canonical
  mechanisms may be referenced as `stable` only after an explicit initial
  classification review; they are not copied into catalog records as new
  authority.
- **Validation:** Strict schema; unique/stable IDs; legal lifecycle
  transitions; resolving source/decision/successor references; no pattern path
  in generated output inventories; independent-evidence gate for
  `recommended`; compatibility/migration requirement for `stable`; valid and
  invalid fixtures.
- **Rollback:** Remove catalog navigation from a future source release while
  retaining deprecated/rejected records and history; generated projects are
  unaffected because they never depend on the live catalog.
- **Affected Blueprint artifacts:** New source-only catalog schema and records;
  `README.md` navigation only after acceptance; `validate_blueprint.py` and
  source acceptance tests.
- **Source audit patterns:** P01, P18, P20.

### PROPOSED-AMENDMENT-B — Clarify semantic, binding, context, and claim envelopes

- **Status:** proposed amendment to existing dossier, harness, and Generation
  Contracts; not a new runtime ADR.
- **Problem:** Current behavior is sound but several related semantics are
  distributed: inferred/intentional omission/display projection; stable versus
  late-bound generator inputs; Context Pack purpose/lifecycle; and explicit
  non-proven implications.
- **Current behavior:** Information roles, unknowns, generated-view
  non-authority, no-transfer generation, source freshness/rights, and evidence
  limitations exist. Context Pack metadata is prose-only and incomplete.
- **Proposed behavior:**
  1. Add one semantic crosswalk without changing per-aggregate statuses.
  2. State the generator's binding classes and revalidation boundary.
  3. Add a machine-checkable optional Context Pack manifest.
  4. Require consequential evidence/proof artifacts to state what they do not
     prove.
- **Invariant:** Derived, inferred, stale, unknown, or intentionally omitted
  information cannot silently become authority, readiness, or an accepted
  project fact; context possession cannot grant action authority.
- **Alternatives considered:**
  - One universal status/trust enum — rejected.
  - Prose-only Context Pack refinement — rejected for cross-boundary stale or
    revoked context.
  - Add all fields to every kernel record — rejected as boilerplate and
    coupling.
  - Do nothing — simpler but leaves context lifecycle unenforceable.
- **Compatibility impact:** Semantic documentation is additive. The Context
  Pack manifest is a new optional versioned contract; it does not alter
  existing kernel records.
- **Migration impact:** Existing generated Context Pack entry points remain
  unassessed. An adopted project reconciles any active pack explicitly; no
  automatic field invention or silent upgrade.
- **Validation:** Golden semantic fixtures; derived-view authority rejection;
  generation leakage fixtures; Context Pack valid/invalid, expiry, revocation,
  recipient, sensitivity, retention, size, and exclusion fixtures; claim
  boundary tests.
- **Rollback:** Revert the source/template/schema addition in a successor
  source release. Existing independent projects retain their adopted snapshot
  and decide locally whether to migrate.
- **Affected Blueprint artifacts:** `dossier/BLUEPRINT.md`,
  `harness/BLUEPRINT.md`, `shared/GENERATION_CONTRACT.md`,
  `dossier/artifact-types.json`, the High-Assurance Context Pack template, a
  new optional context-pack schema, generator schema inventory, and tests.
- **Source audit patterns:** P02, P06, claim portion of P18, P19.

### PROPOSED-SRC-DEC-C — Add one conditional Architecture Proof artifact family

- **Status:** proposed.
- **Problem:** Decisions, tasks, evaluations, and evidence exist, but a risky
  architecture experiment has no standardized hypothesis/stop/adversarial/
  non-proof contract.
- **Current behavior:** Projects can compose existing records manually;
  Blueprint's own migrations and acceptance tests demonstrate the discipline
  without exposing it as an optional reusable artifact.
- **Proposed behavior:** Add one `architecture-proof` family with selectable
  proof kinds (`spike`, `reference_slice`, `provider_qualification`,
  `adversarial_fixture_pack`, `readiness_evidence`). A large source-disposition
  companion is conditional, not automatically created.
- **Invariant:** A completed template, accepted decision, successful happy
  path, or passing local test proves only the exact hypothesis and scope its
  evidence supports.
- **Alternatives considered:**
  - Separate package for every proof kind — rejected as duplication.
  - Make proof mandatory for every decision — rejected as disproportionate.
  - Reuse only the task template — insufficient for stop criteria,
    adversarial scope, and explicit non-proof claims.
- **Compatibility impact:** Additive optional source template and schema. No
  default generated path.
- **Migration impact:** None. A later decision may add it to High Assurance,
  which would require artifact-taxonomy/profile/generator migration analysis.
- **Validation:** Valid/invalid contract fixtures, exact subject/version,
  acceptance and stop criteria, at least one adversarial condition when risk
  requires it, evidence links, supported/unsupported/inconclusive result,
  rollback/cleanup, skipped checks, limitations, and non-proven implications.
- **Rollback:** Deprecate the source template with a successor; no generated
  project is affected by default.
- **Affected Blueprint artifacts:** Pattern Catalog record; optional schema and
  templates; source validation. Do not alter profile inventories in the first
  change.
- **Source audit patterns:** P20 and relevant proof aspects of P11, P14, P16,
  P17.

### PROPOSED-SRC-DEC-D — Admit lifecycle and governed change/effect patterns without scaffolding them

- **Status:** proposed catalog-admission decision, not package implementation
  or project adoption.
- **Problem:** P05, P11, P15, and P17 contain reusable failure-prevention
  lessons, but twelve separate packages would duplicate existing operations,
  task, Git, evidence, and lifecycle mechanisms and burden simple projects.
- **Current behavior:** Concrete repository-local variants exist. Generic
  durable-temporary-resource, candidate-impact, idempotent external-effect,
  and typed ambiguous-recovery contracts do not.
- **Proposed behavior:**
  - Admit `lifecycle-disposition` as a `reviewed` optional pattern.
  - Admit `governed-change-and-effects` as a `reviewed` modular pattern with
    independently triggered `impact`, `action`, `mutation_effect`, and
    `recovery_incident` modules.
  - Do not generate, scaffold, or mark either `recommended` until an exact
    project adoption and proof demonstrate the contracts.
- **Invariant:** Optional application mechanisms cannot become a second
  universal kernel; action selection is not authorization; external
  acknowledgement is not truth; compensation is not rollback; cleanup cannot
  destroy required evidence.
- **Alternatives considered:**
  - Four or more independent packages — rejected initially because their
    ownership, effect, evidence, and recovery records overlap.
  - One universal governed-action pipeline — rejected as application
    architecture.
  - Reject all patterns — loses reusable lessons already partially evidenced
    by Git, refresh, migrations, and operations.
- **Compatibility impact:** Source-only reviewed records. No generated path,
  schema, profile, or kernel change.
- **Migration impact:** None until a later experimental package decision.
- **Validation:** Catalog completeness and no-generation tests now. A later
  experimental package must pass the pattern-specific failure tests in the G
  section below.
- **Rollback:** Mark the record `rejected` or `deprecated` with rationale; no
  generated project is affected.
- **Affected Blueprint artifacts:** Pattern Catalog records only in the first
  change.
- **Source audit patterns:** P05, P11, P15, P17, with P06 as an impact-input
  refinement.

## Pattern Catalog governance decision

The review recommends maintaining the catalog only under
PROPOSED-SRC-DEC-A. Its architectural placement is:

```text
Universal kernel and canonical generation contracts
    ↓ restrictions and stable invariants only
Source-only governed pattern catalog
    ↓ optional knowledge; no permission or automatic generation
Project-owned adoption decision or bounded implementation choice
    ↓ project specialization and project evidence
Project-specific implementation
```

A catalog record may describe a known Blueprint implementation, but the
record is not that implementation's authority source. A `stable` catalog
pattern is still optional unless a separate canonical decision promotes a
specific invariant into the kernel. Kernel admission requires the prompt's
ten-part placement test plus explicit compatibility and migration review.

## E. Context Pack impact review

### Current contract

The current High-Assurance template requires:

- audience;
- task class;
- authoritative source links;
- an exact freshness rule;
- size budget;
- excluded history;
- owner; and
- a clear non-authority boundary.

This is a sound optional baseline, but it is navigation prose rather than a
validated envelope.

### Proposed optional manifest

Every adopted cross-boundary Context Pack should represent the following
fields explicitly. A value may be `not_applicable` only where the schema
requires a rationale; omission is not an assessment.

| Field group | Required semantics |
|---|---|
| Identity | stable pack ID, schema version, pack version, owner |
| Purpose and consumer | exact purpose, recipient/consumer, task class, scope |
| Sources | stable source refs, exact version/revision/digest, information role and authority/status, transformation or selection basis |
| Time | created/observed time, freshness rule, `valid_until`, revalidation method |
| Disclosure | sensitivity/data class, allowed use, rights/use restrictions, egress/recipient constraints, minimization basis |
| Lifecycle | retention/deletion rule, invalidation triggers, revocation state/reason/successor, stale/revoked-use behavior |
| Bounds | size budget, actual size, exclusions and excluded history |
| Claims | limitations, unresolved inputs, `permission_grant: false`, explicit statement that receipt does not establish capability or authority |

The manifest can point to context content without duplicating it. Enforcement
outside the repository—such as provider retention or deletion—still requires
project-specific controls and evidence; schema conformance cannot manufacture
that behavior.

### Accepted refinement and source-capability proof

| Change | Deterministic proof required |
|---|---|
| Pattern Catalog | Schema valid/invalid fixtures; duplicate/stable ID checks; legal lifecycle transitions; source/successor resolution; `recommended` independent-evidence gate; `stable` compatibility/migration gate; no catalog asset in generated profiles; no permission/adoption inference |

### Proof gates for reviewed patterns before implementation

| Pattern/module | Required project-supplied proof before `experimental` or package implementation |
|---|---|
| Lifecycle disposition | Exact durable temporary resource; owner and lifecycle boundary; orphan/retention failure observed or credibly modeled; expiry/cleanup; evidence dependency; sensitive-data minimization; recreate-versus-retain tradeoff |
| Candidate impact/action | Real resolver or consequential candidate; stale-base and changed-dependency cases; complete affected-path/resource/policy envelope; explicit no-op/decline/defer/unresolved behavior; unauthorized effect rejection |
| Governed mutation/effect | Exact authoritative owner and external boundary; CAS/stale writer; idempotency; duplicate dispatch; crash before/after commit; timeout/read-back; unknown outcome; no-blind-retry; compensation |
| Typed recovery/incident | Actual failure classes and point of no return; retry versus reconcile versus compensate versus abandon; safe unaffected work; residual consequence; operator escalation; incident reconstruction |
| Resource accounting | Owned quantity and unit; logical/provider mapping; conservation within uncertainty/loss; concurrent reservation; expiry/release; reconciliation; unit and rounding boundaries |
| Bounded invalidation | Measured rebuild cost; complete dependency-edge claim; missing-edge fault injection; conservative widening; unrelated-output stability; full rebuild fallback |
| Corpus use | Exact source corpus and rights; separate retrieve/extract/fixture/evaluate/train/redistribute/publish decisions; provenance manifest; revocation; prohibited-use fixtures; no policy or authority inference |

Documentation-only enforcement is insufficient for Context Pack lifecycle,
catalog lifecycle/promotion, or any future governed-effect implementation.
Those failures require schemas and executable valid/invalid/adversarial tests.

## Adversarial architecture review

The contrary hypothesis was applied before recommending any shared change:
what becomes simpler, safer, or more correct if Project Blueprint does not
adopt the proposal?

| Proposal challenged | Benefit of not adopting | Residual risk of not adopting | Resulting constraint |
|---|---|---|---|
| Pattern Catalog | No new schema, curation, compatibility, or implied-endorsement surface | Project-local patterns can be promoted informally or repeatedly rediscovered | Accept only as source-only, non-generating, lifecycle-governed capability |
| Semantic crosswalk | Avoids another vocabulary and status confusion | Similar meanings remain scattered and reviewers may conflate them | Documentation crosswalk only; no universal enum or new lifecycle |
| Staged-binding amendment | Existing generator already behaves correctly | Future generators may bind mutable project/provider facts early | Add a narrow source-contract explanation and leakage fixtures, not a new runtime system |
| Context Pack manifest | Prose packs stay lightweight | Stale, revoked, overbroad, or wrong-recipient packs cannot be rejected deterministically | Optional manifest only when CTX-0001 is adopted across a material boundary |
| Architecture proof | Small decisions avoid unnecessary ceremony | Risky choices can be declared proven by a happy-path prototype | Conditional source template, never required for routine decisions |
| Lifecycle disposition | No temporary-resource registry or cleanup bookkeeping | Durable costly/sensitive temporary state can become orphaned | Reviewed optional pattern with a materiality trigger |
| Governed action/impact | Simple projects avoid an action algebra and impact forms | Consequential candidates can hide blast radius or refusal semantics | Project-specialized optional modules; no universal verbs |
| Mutation/effect/recovery | Avoids premature distributed-systems complexity | External timeouts, duplicate effects, and fictional rollback remain recurring hazards | Catalog admission now; no implementation without a real effect boundary |
| Resource accounting | Avoids false precision and ledger machinery | A future project may rediscover unit/conservation rules | Defer until an owned quantitative resource exists |
| Bounded invalidation | Full refresh remains simple and safe | Expensive derived systems may rebuild too much | Defer until measured cost and complete dependencies exist |
| Policy locks | Avoids implying generic specialist authority | A future regulated project may need executable current-policy gating | Use project restriction extensions when triggered; no generic lock now |
| Corpus governance | Avoids an unused rights/training ontology | Future AI/content projects may conflate distinct permissions | Defer machinery; retain the non-conflation principle in catalog governance |

No recommended change survives by being universally useful. It survives only
because its placement prevents optional complexity from entering ordinary
generated projects.

## Final decision report

### Already embodied

#### P01 — Domain-neutral kernel and extension boundary

The exact current mechanisms are the five-layer architecture, closed
restrictions-only extension API, independent snapshot rule, profile
inventories, and authority-expansion/disable fixtures. No architectural change
is required.

#### P03 — Orthogonal identity, version, representation, record, and lifecycle

The three-level dossier identity model, stable record IDs, explicit schema
versions, successor semantics, and separate task/decision/artifact lifecycles
already satisfy the invariant. A universal status model is rejected.

#### P07 — Typed sources and derived renditions

The authoritative project artifact registry, strict JSON schemas,
transactional refresh, generated catalog/path-authority/manifest roles, and
typed migrations already implement the source/derived contract.

#### P09 — Heuristics do not govern

Readiness is dependency-derived, recommendations are non-authorizing, dates do
not choose work, metrics cannot infer readiness, and selection among eligible
items requires current direction or an accepted decision.

#### P12 — Human agency and proportional friction

Current authority tiers, named-risk ceremony, safe local workflows, optional
approval evidence, and review-capacity limits already prevent both silent
automation and universal confirmation ceremony.

#### P13 — Effective capability readiness

Tool availability, operation permission, capability provenance, compatible
kernel version, trust/adoption status, command evidence, and readiness remain
separate. Live provider facts stay project-specific.

#### P14 — Exact provenance, rights, validity, and revocation

Source, capability, approval, evidence, and decision contracts already cover
exact version or fingerprint, rights/license, sensitivity, freshness, validity,
revocation, limitations, and successor semantics. No generic specialist lock
is warranted.

#### P16 — Deterministic governance around probabilistic output

Model/generated/imported material is non-authoritative data; deterministic
policy, schemas, lifecycles, validators, and external authority govern
acceptance and effects. No AI implementation belongs in the kernel.

### Refinements

#### P02 — State and projection crosswalk

Add one concise semantic crosswalk for authority/observation/inference/
proposal/derivation/history/staleness/unknown/intentional omission. Preserve
each aggregate's current status vocabulary and make display readiness a named
non-writing derivation.

#### P06 — Generation binding semantics

Document source-stable, generation-time identity, project-owned unresolved,
and execution-volatile inputs. Preserve strict unresolved-template failure and
revalidate volatile facts only at a consequential project boundary.

#### P18 — Pattern promotion and evidence claims

Keep existing evidence-boundary behavior. Add source-only catalog admission,
promotion, deprecation, rejection, and independent-evidence rules. Defer
corpus-use implementation.

#### P19 — Context Pack contract

Add a versioned optional manifest for purpose, consumer, scope, exact source
status/version, validity, sensitivity/use, retention, invalidation, revocation,
exclusions, size, owner, limitations, and non-authority. Prose alone is not
enough for an adopted cross-boundary pack.

### New accepted opportunities

These engineering-review recommendations are now bounded by the accepted
source decision mapping above. This section retains the reviewed rationale;
`ARCHITECTURE_DECISIONS.md` records the authoritative accepted scope.

#### Universal additions

No new universal runtime mechanism is accepted. The only shared additions are
source-governance or semantic-contract refinements:

- source-only Pattern Catalog governance;
- the state/projection crosswalk;
- staged-binding language in the Generation Contract; and
- the optional machine-checkable Context Pack contract.

#### Optional patterns and packages

- One conditional `architecture-proof` family is accepted for design,
  combining spike, reference-slice, provider-qualification, adversarial-pack,
  and high-assurance decision evidence.
- `lifecycle-disposition` is accepted as a reviewed optional pattern, not a
  default profile artifact.
- `governed-change-and-effects` is accepted as a reviewed modular pattern for
  impact, typed action, mutation/effect, and recovery/incident semantics. Its
  implementation remains trigger-gated.

#### Proof/evaluation tooling

The Architecture Proof family must have strict valid/invalid fixtures and
explicit non-proof claims. Future governed-effect modules require
concurrency/failure injection rather than documentation-only assurance.

### Conditional / deferred patterns

#### P04 and P10 — Resource units, accounting, and reservations

Reconsider only when an adopting project owns a fungible measurable resource,
crosses a logical/provider unit boundary, and must prevent overcommitment or
reconcile external observation. Authority and leases never satisfy this
trigger.

#### P08 — Bounded invalidation

Reconsider only when full regeneration has measured material cost and the
project can prove sufficiently complete typed dependencies plus a conservative
fallback. A graph database is never the trigger.

#### P11, P15, and P17 implementation

The patterns may enter the source catalog as `reviewed`, but schemas,
generated paths, and project packages remain deferred until a concrete
adopter supplies its durable partial-work, action-impact, concurrency, or
external-effect failure model.

#### P14 policy locks

Reconsider a reusable lock only when at least one project-specific restriction
extension demonstrates versioned current-policy gating, expiry/revocation,
waiver authority, descendant impact, and specialist ownership that the
existing security/supply-chain entry point cannot express.

#### P18 corpus use

Reconsider only when Blueprint or an adopter actually retrieves, extracts,
builds fixtures from, evaluates on, trains on, redistributes, or publishes a
material corpus across a trust or rights boundary.

### Rejected transfers

The following are rejected and should remain in the handoff rationale:

- MFMS ingredients, recipes, lots, household entities, meal actions, culinary
  roles, food states, planning periods, rescue modes, and UX labels;
- modular monolith plus relational persistence as a Blueprint default;
- one universal Project aggregate, graph, status enum, lifecycle enum, action
  enum, trust Boolean, readiness Boolean, database, or provider topology;
- conservation and reservation semantics for authority, credentials,
  capability registration, coordination leases, or non-quantitative
  exclusivity;
- confirmation or high-assurance ceremony for every reversible local action;
- retrieval-before-generation as an absolute rule for explicitly creative
  work;
- external acknowledgement as authoritative outcome;
- rollback language for an irreversible or ambiguous external effect;
- evidence, provenance, model confidence, similarity, checksums, tests,
  templates, or prior approval treated as legal/safety/security/rights
  authority they cannot grant; and
- automatic promotion from one project, one successful spike, usage count, or
  a completed template into Blueprint canon.

## Implementation decision gate

The gate was satisfied by explicit repository-owner authorization for the
scope mapped to `SRC-DEC-0003` through `SRC-DEC-0006`. Implementation remains
bounded by those accepted decisions: `SRC-DEC-0006` admits records to the
catalog only, and no catalog record is permission to generate, scaffold,
recommend, or adopt its pattern. Deferred mechanisms remain deferred until
their documented project-owned applicability and proof triggers are met.

## Review limitations

- The review is bound to the exact repository revision named above.
- The primary handoff was verified by digest and read in full.
- The source audit's classifications were treated as proposals, not facts.
- No literal MFMS source mechanism was required to resolve an ambiguity; the
  underlying decision corpus was therefore not used to import or re-decide
  MFMS semantics.
- The initial source validator passed. Final validation after adding this
  review artifact is recorded in the task handoff, not retroactively claimed
  here.
- Structural validation cannot accept these proposed decisions or prove that
