# Migration: 1.0.1 to 2.0.0

This is a breaking blueprint and harness-kernel migration. Version `2.0.0`
makes dependency readiness executable rather than merely descriptive.
Generated projects are independent snapshots and never upgrade automatically.

## Contract changes

- `harness.task.v2` restricts `dependencies` to hard `TASK-####`
  prerequisites and adds `plan_item_refs`, `gate_refs`, and `blocking_refs`;
- `project.dossier.plan.v2` restricts `depends_on` to hard `PLAN-####`
  prerequisites and adds reciprocal `task_refs` and structured
  `blocking_refs`;
- `harness.lifecycle.v2` routes `blocked` and `reopened` tasks through `ready`
  before execution and permits `ready` to become `blocked`;
- `harness.project.v2` replaces legacy command strings with deliberately
  assessed `configured`, `not_applicable`, or pre-adoption `not_assessed`
  hooks; configured commands use direct argv, a same-executable version probe,
  owners, freshness, and declared effects;
- `harness.validators.v2` adds the read-only frontier plus separately explicit
  project-check evidence and adoption-verification commands;
- `.agent/project-checks/evidence.json` and its explicit writer separate
  structural conformance from project adoption and demonstrated readiness;
- the `ready` gate requires completed hard dependencies, passed or validly
  waived gates, resolved structured blockers, and consistent plan links;
- validation rejects task and plan cycles, execution against incomplete
  predecessors, unresolved gates/blockers, contradictory plan/task status,
  and nonreciprocal links;
- `python -B .agent/scripts/validate.py --ready-frontier` derives eligible
  plan items and tasks without writing or granting authority; and
- timestamps and external deadlines remain constraints or evidence metadata;
  they never satisfy prerequisites or select priority.

## Authority boundary

Do not copy `2.0.0` files over an active `1.0.1` project. Read target
instructions, inspect accepted decisions and active records, and perform the
migration as a project-specific authorized change. A derived frontier is not
permission, approval, or a project priority decision.

## Required sequence

1. Run the `2.0.0` adoption planner read-only and retain its output as
   migration evidence.
2. Inventory every live task and structured plan item. Preserve IDs; do not
   reuse or silently reinterpret them.
3. Classify each existing task `dependencies` entry. Keep only hard
   `TASK-####` prerequisites there. Move plan links to `plan_item_refs`, gates
   to `gate_refs`, and status-bearing nonprecedence blockers to
   `blocking_refs`. Record advisory relationships in project documentation or
   a registered extension rather than the hard DAG.
4. Classify each plan `depends_on` entry. Keep only hard `PLAN-####`
   prerequisites. Add reciprocal `task_refs`/`plan_item_refs` pairs and move
   nonprecedence blockers to structured `blocking_refs`.
5. For each free-text blocker, create or identify a status-bearing task, plan,
   gate, decision, or RAIDQ record. Retain `blocked_by` as explanation, not as
   the machine-resolvable cause.
6. Reassess every `ready`, `in_progress`, `validating`, `review`, and
   `completed` task. A task whose hard dependency reopened, whose gate is no
   longer passed/waived, whose blocker is active, or whose plan link is
   inconsistent must move through the project's controlled correction path;
   do not preserve an invalid status merely to make migration pass.
7. Reassess every `in_progress` and `completed` plan item. Link execution tasks
   reciprocally; require all linked tasks and closure evidence before plan
   completion.
8. Adopt the v2 lifecycle deliberately. A blocked or reopened task returns to
   `ready`, never directly to `in_progress`, so readiness is re-evaluated.
9. Configure the new `ready_frontier` command and update instructions,
   workflows, handoff, and closure guidance. If several items are ready,
   preserve current operator direction or an accepted priority/value/risk
   decision as the selection basis; do not derive priority from dates.
10. Assess every project test, lint, build, and closure hook. Never parse a
    legacy string into argv. Configure a safe v2 argv contract from current
    project evidence, record an owned `not_applicable` rationale, or preserve
    `not_assessed` only while the harness remains pre-adoption.
11. Refresh derived artifacts, run configured target-project checks only
    through the separately explicit evidence writer, then run the v2 read-only
    check, frontier command, and mutation suite.
12. Append the migration event to `.project-blueprint-origin.json` through the
    project's authorized migration mechanism while preserving
    `initial_generation`.

## Executable reference fixtures

The repository contains a closed reference-bundle reconciler and deterministic
fixtures for the changed task, plan, lifecycle, project-command, validator,
and origin contracts:

```text
python3 -B skills/project-bootstrap/scripts/test_migration_1_0_1_to_2_0_0.py
python3 -B skills/project-bootstrap/scripts/migrate_1_0_1_to_2_0_0.py \
  --input skills/project-bootstrap/fixtures/migrations/1.0.1-to-2.0.0/valid/v1-standard.json \
  --check
```

To materialize the reference result, pass `--output` with a new path. The tool
refuses in-place or existing-path output. It is not a general in-place project
upgrader: a target project still owns reconciliation, authorization, evidence,
and adoption. It does not run legacy or migrated project commands.

## Verification

Migration is complete only when:

- task and plan records validate against their v2 schemas;
- both hard-dependency graphs are acyclic and all references resolve;
- active execution/review/completion states have completed predecessors,
  satisfied gates, resolved structured blockers, and coherent reciprocal
  links;
- blocked states have an unresolved structured cause and an explanatory
  `blocked_by` entry;
- completed plan items link only completed tasks and closure evidence;
- the ready-frontier command is read-only, deterministic for the same source
  records, and excludes ineligible work;
- no date or deadline is treated as satisfying a dependency or silently
  selecting work; and
- a second application to the validated result is an exact no-op, ambiguous or
  mixed-authority input fails closed, and the exact input bytes remain embedded
  as noncurrent rollback evidence; and
- refresh, full validation, target checks, and mutation tests pass on the exact
  migrated revision with limitations and external effects disclosed.

## Rollback

Retain the exact pre-migration revision as noncurrent evidence. The reference
result embeds the exact UTF-8 input bytes, their digest, and the parsed v1 live
state without making it current authority. Rollback remains a separately
authorized project action and restores the v1 task, plan, lifecycle, project,
validator, and origin contracts together. Because rollback evidence embeds the
input verbatim, it inherits that input's sensitivity, access, and retention
requirements. Never mix live v1 and v2 authority.
