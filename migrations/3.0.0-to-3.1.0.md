# Migration: Project Blueprint 3.0.0 to 3.1.0

## Classification

This is an additive Blueprint/source-generator transition. The harness kernel
remains `3.0.0`; existing aggregate status vocabularies, extension authority,
and default runtime behavior do not change.

Generated projects are independent snapshots. Nothing in this migration
updates a project automatically, imports source decisions, or grants
permission.

## Source-only additions

The following remain in the Blueprint source bundle and must not be copied
into a generated project as adoption state:

- `ARCHITECTURE_DECISIONS.md`;
- the `patterns/` catalog, records, schemas, fixtures, and Architecture Proof
  templates; and
- `shared/source-contracts/information-state-semantics.json`.

They require no generated-project migration.

## Generated-profile delta

- Minimal: no new governed path or optional-contract schema.
- Standard: no new governed path or optional-contract schema.
- High Assurance: a newly generated 3.1.0 snapshot includes
  `.agent/schemas/context-pack-manifest.schema.json` for the existing optional
  CTX-0001 entry point. It does not include a Context Pack manifest or mark
  CTX-0001 applicable.

The Blueprint and generator provenance versions advance to `3.1.0`. The
origin's `harness_kernel_version` and generated `.agent/schema.json` remain
`3.0.0`.

The 3.1.0 source generator also enforces a versioned generation-disposition
policy. Version 2 explicitly lists reviewed inputs. Runtime generation ignores
and reports unreviewed additions, blocks missing or unsafe inputs only for
profiles that require them, and preserves strict hard boundaries at final
generation. Repository validation remains strict across all profiles. This
changes no declared Minimal, Standard, or High-Assurance output inventory, so
existing snapshots require no migration for the enforcement refinement.

## Existing project reconciliation

Do not replace an existing project snapshot or copy the new schema over its
authority. If a 3.0.0 High-Assurance project has an applicable cross-boundary
Context Pack need:

1. inspect the project's current CTX-0001 applicability, owners, sources,
   retention rules, provider boundary, and evidence;
2. create a project-owned migration/adoption decision if its governance model
   requires one;
3. add the v1 Context Pack schema as a new project-governed contract;
4. reconcile each active prose pack manually into a new manifest without
   inventing purpose, consumer, scope, versions, authority status, validity,
   sensitivity, rights, retention, revocation, or limitations;
5. preserve unconverted packs as unassessed or historical rather than silently
   treating them as valid manifests; and
6. run project-local schema, expiry, revocation, scope, sensitivity, retention,
   exact-source, non-authority, refresh, and read-only validation.

Projects without an applicable Context Pack trigger make no change. Existing
records are never silently converted.

## Rollback and compatibility

Because the source-only assets are absent from generated inventories, removing
their navigation in a future source version cannot change an existing
project. A project that deliberately adopts the Context Pack v1 schema owns
its copy and must use a project-specific successor or removal decision.

Structural migration or schema validation does not prove harness adoption,
specialist compliance, provider deletion, or project readiness.
