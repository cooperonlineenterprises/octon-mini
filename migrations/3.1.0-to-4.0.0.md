# Migration: Project Blueprint 3.1.0 to 4.0.0

This is a major, project-owned migration to the velocity kernel. Nothing in
this guide updates a project automatically, grants permission, adopts the
harness, or establishes target-project readiness.

## Required path

1. Preserve the independent 3.1.0 snapshot and current project content.
2. Run read-only inspection and preserve its target-bound hashes:

   ```text
   python3 skills/project-bootstrap/scripts/migrate_3_1_0_to_4_0_0.py inspect \
     --target /absolute/project --output /absolute/review/inspection.json
   ```

3. Build the closed review file from actual 3.1 release/source evidence. For
   every static generated path, record its exact old pristine SHA-256 and mode,
   or stop and reconcile it manually. Derived/provenance paths use their
   explicit confirmation classes. Bind authority and evidence references,
   layout, origin/project preimages, rationale, and limitations. The seed
   command refuses assessed legacy collaboration because it may not discard or
   reinterpret project facts.
4. Create and check the deterministic non-applied seed:

   ```text
   python3 skills/project-bootstrap/scripts/migrate_3_1_0_to_4_0_0.py seed \
     --target /absolute/project --review /absolute/review/review.json \
     --output /absolute/review/seed.json
   python3 skills/project-bootstrap/scripts/migrate_3_1_0_to_4_0_0.py check \
     --target /absolute/project --seed /absolute/review/seed.json
   ```

   The seed supplies inventory data to the upgrader; it is never applied to the
   project directly. It seeds collaboration v2 as unassessed and never infers
   collaborators or a workflow.
5. Run `pb upgrade plan --legacy-seed /absolute/review/seed.json` with current
   project-owned authority and evidence.
6. Review every authority-bearing, project-owned, modified, deleted, moved,
   permission, symlink, stable-ID, and collision classification. Do not use a
   force bypass; none is provided.
7. Apply only the exact reviewed digest. The transaction stages refresh,
   structural validation, and the complete release tier before writing, then
   records exact rollback preimages.
8. Reassess collaboration, SCM, trigger packages, project hooks, harness
   adoption, and readiness as separate project-owned activities.
9. Reconcile decision governance explicitly:
   - accept the new empty `.agent/decisions/governance-register.json` only when
     the path is noncolliding; preserve any existing project-owned workbook or
     register for manual crosswalk;
   - inventory material unresolved questions from existing decision, RAIDQ,
     plan, gate, and handoff sources and assign new stable `DREG-####` tracking
     IDs without renaming or reusing existing `DEC-####` IDs;
   - link accepted entries only to currently accepted `DEC-####` authority and
     add the reciprocal `DREG-####` to that record's
     `governance_register_refs`; do not infer this link for an unrelated
     historical decision; keep recommendations and owner selections in their
     separate fields;
   - reconcile every dashboard row, decision object, review, dependency, and
     closure item; and
   - merge the subordinate-handoff checklist without overwriting a project
     handoff. Copy status only through validated claim markers or prefer links.
10. Leave every requirement and gate maturity assessment absent or unassessed
    until project-specific evidence supports it. Do not infer maturity from a
    prior structural pass, completed document, selected option, or generated
    scaffold.

## Contract changes

- Blueprint and harness kernel advance to 4.0.0.
- The compact dossier layout becomes the default for new snapshots; existing
  separated layouts remain supported and are never silently compacted.
- `state/current.json` becomes fully derived; operator intent moves to
  `state/focus.json`.
- Collaboration evidence advances to the progressive v2 contract without
  inferring people or adopting a workflow.
- The Git portfolio and domain packages become content-addressed triggered
  installations instead of universal payload.
- Origin provenance advances to v2 with an installed-inventory v2 baseline.
- Proposal, transaction, diagnostic, package, SCM, hook-candidate, focus, and
  upgrade contracts are added.
- The existing `DEC-0001` concern gains a strict decision-governance register,
  owner workbook, gate-first trade-off review, read-only review report, handoff
  reconciliation, and minimum closure graph. Durable accepted decision
  lifecycle and existing `DEC-####` records remain unchanged.
- Requirement and gate schemas accept an optional scoped seven-level maturity
  assessment with an exact level-specific basis kind. Omission remains
  backward compatible; no validator promotes it.

## Rollback and recovery

An apply writes a pending journal before target mutation. Interrupted applies
must use explicit recovery. A completed receipt embeds exact preimages;
an exact surviving terminal receipt is finalized without undoing its result.
Rollback is durably resumable and refuses any path outside its exact preimage
or post-apply state. Derived repair remains a separate explicit writer, and
project-check evidence remains separate from generated-integrity writes.

Existing records are never silently converted, stable IDs are never
reassigned, and preserved project-modified files retain their earlier pristine
baseline so later upgrades continue to require review.
