# Migration: Project Blueprint 3.x to Octon Mini 4.0.0

This transition is named **Project Blueprint 3.x to Octon Mini 4.0.0**. The
executable path below accepts an exact Project Blueprint 3.1.0 snapshot. An
earlier 3.x snapshot must first reach that supported baseline through its
closed historical migration or receive project-specific specialist review.

This is a major, project-owned product, command, protocol, provenance, skill,
and generated-path migration. Nothing in this guide updates a project
automatically, grants permission, adopts the harness, or establishes
target-project readiness.

## Clean-break boundary

- Legacy `pb`, `.agent/scripts/pb.py`, `.agent/scripts/pb_doctor.py`,
  `.agent/scripts/pb_finish.py`, `.agent/scripts/pb_transaction.py`, and
  `.project-blueprint-origin.json` are accepted only as inert input paths whose
  bytes and metadata can be reviewed and fingerprinted.
- Neither the inspector nor the upgrader imports, dispatches, or executes a
  legacy `pb` launcher or module.
- A successful transaction explicitly deletes those reviewed legacy paths and
  creates `octon`, `.agent/scripts/octon.py`,
  `.agent/scripts/octon_doctor.py`,
  `.agent/scripts/octon_work_completion.py`,
  `.agent/scripts/octon_transaction.py`, and `.octon-mini-origin.json`.
- No `pb` alias, warning shim, wrapper, symlink, parser branch, or compatibility
  mode is installed.
- A second application is an exact no-op refusal once the current Octon Mini
  origin exists and the legacy origin is absent.

## Required reviewed path

1. Preserve the independent Project Blueprint snapshot and all current
   project-owned content.
2. From the current Octon Mini Project Bootstrap source or a current installed
   skill package, run the read-only inspector:

   ```text
   python3 skills/octon-mini-project-bootstrap/scripts/migrate_3_1_0_to_4_0_0.py inspect \
     --target /absolute/project --output /absolute/review/inspection.json
   ```

   The inspector reads legacy paths as data. It makes no target-project write
   and does not run `pb`.
3. Build a review with schema
   `octon-mini.bootstrap.cross-brand-migration-review.v1`. Bind it to:
   - source product `project-blueprint` and version `3.1.0`;
   - target product `octon-mini` and version `4.0.0`;
   - the exact legacy origin and project-contract hashes;
   - current project-owned authority and evidence references; and
   - every recorded generated path, role, policy, old mode, old pristine hash,
     confirmation, and rationale.

   If a static baseline is unknown, stop for specialist reconciliation.
   Derived and provenance entries stay hash-free. Assessed legacy
   collaboration is not reset or inferred by this migration.
4. Create and verify the deterministic, non-applied cross-brand seed:

   ```text
   python3 skills/octon-mini-project-bootstrap/scripts/migrate_3_1_0_to_4_0_0.py seed \
     --target /absolute/project --review /absolute/review/review.json \
     --output /absolute/review/seed.json
   python3 skills/octon-mini-project-bootstrap/scripts/migrate_3_1_0_to_4_0_0.py check \
     --target /absolute/project --seed /absolute/review/seed.json
   ```

   The seed uses
   `octon-mini.bootstrap.cross-brand-migration-seed.v1`. It is planning
   evidence and is never written directly into the target.
5. Run the current source dispatcher, not the target's legacy launcher:

   ```text
   ./octon upgrade plan \
     --target /absolute/project \
     --project-blueprint-seed /absolute/review/seed.json \
     --authority-source authority:CURRENT-PROJECT-AUTHORITY \
     --evidence-ref EVD-0001 \
     --output /absolute/review/upgrade-proposal.json
   ```

6. Review every authority-bearing, project-owned, modified, added, deleted,
   moved, permission, symlink, stable-ID, and collision classification. The
   legacy origin and runtime deletions must be visible review items; there is
   no force bypass or silent overwrite exception.
7. Bind an `octon-mini.bootstrap.upgrade-review.v1` review to the exact
   proposal digest. Create the final transaction plan from that proposal and
   review, then apply only its exact accepted digest through `octon upgrade
   apply`.
8. Confirm the migrated snapshot contains only the current command/runtime and
   provenance paths, then run `./octon check`. Structural success is not a
   readiness or adoption claim.
9. Reassess collaboration, SCM, packages, project hooks, work completion,
   harness adoption, and readiness as separate project-owned activities.

## Project-owned reconciliation

- Preserve accepted authority, decisions, tasks, plans, evidence, receipts,
  and stable IDs. Historical `PBV-##` workstream IDs remain unchanged.
- Preserve project facts and locally modified content unless the exact review
  accepts a candidate or deletion.
- Keep collaboration unassessed when the supported legacy baseline was
  unassessed. Never infer collaborators or select a workflow during migration.
- Keep governed work completion disabled. Its current implementation path is
  `.agent/scripts/octon_work_completion.py`; enabling it later remains a
  separate, currently authorized, reviewed action.
- Reconcile decision-governance and dossier additions without overwriting
  project-owned registers, questions, handoffs, or accepted decisions.
- Leave requirement and gate maturity absent or unassessed until
  project-specific evidence supports it.

## Contract and namespace changes

- Product identity changes from Project Blueprint 3.x to Octon Mini 4.0.0.
- The command changes from `pb` to `octon`, with no compatibility surface.
- The project contract advances to `harness.project.v5` and records
  `octon_mini_version`.
- Current origin provenance is `octon-mini.project.origin.v1` at
  `.octon-mini-origin.json`; installed inventory is
  `octon-mini.project.installed-inventory.v1` and records capability roles plus
  `baseline_product` and `baseline_version`.
- Migration events use `octon-mini.project.migration.v1` with explicit source
  and target products and versions. Earlier Project Blueprint migration events
  are translated without changing their stable `MIG-####` IDs or historical
  meaning.
- Current schema IDs use `https://octon-mini.local` and capability-qualified
  `octon-mini.*` protocol identifiers. Legacy `project-blueprint.*` values are
  retained only in inspected preimages, converted historical provenance, and
  explicit migration handling.
- The compact dossier layout is the default for new snapshots. An established
  separated layout remains separated unless a different layout change is
  separately reviewed.
- Collaboration evidence advances to its current contract without inferring
  people, authority, or workflow adoption.
- State, diagnostics, transactions, packages, SCM, hook candidates, guided
  setup, and work completion use the current Octon Mini protocols and current
  descriptive runtime paths.

## Rollback and recovery

Apply writes a pending journal before target mutation. Interrupted apply must
use explicit recovery. A completed receipt embeds the exact preimages for each
reviewed deletion or replacement and the exact postimages for each creation or
replacement.

Rollback is invoked through the current `octon transaction rollback` command
while that current runtime exists. It is durably resumable and refuses a path
that differs from its exact post-apply state. A successful rollback restores
the exact Project Blueprint origin/runtime preimages and removes the newly
created Octon Mini paths; restored legacy files are not executed by the
migration tooling.

Derived repair remains a separate explicit writer. Project-check evidence
remains separate from generated-integrity writes. Existing records are never
silently converted, stable IDs are never reassigned, and preserved
project-modified files retain their earlier reviewed baseline so later
upgrades continue to require review.
