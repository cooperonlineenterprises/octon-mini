# Octon Mini 4.0.0 to 4.1.0

This is an explicit reviewed same-product snapshot upgrade. Nothing in this
guide updates a project automatically or adopts the optional long-running-work
capability.

## Added source behavior

- a dormant `octon work run` dispatcher;
- the `long_running_work` trigger assessment, initially `not_assessed`;
- the `workflow_capability` package kind;
- package update-receipt validation and safe unused-package removal; and
- source support for the separately installed `long-running-work` package.

The package payload and `.agent/work-runs/` state are absent after upgrade.
Installation requires a later content-addressed package transaction. Adoption
requires a separate accepted project decision. Neither step grants task or
external-effect authority.

## Procedure

1. Preserve the exact 4.0.0 origin inventory and current project status.
2. Run the current `octon upgrade plan` against the 4.0.0 snapshot.
3. Review every nonautomatic classification. Exact-pristine implementation
   assets may update automatically; project configuration requires an explicit
   reviewed candidate disposition.
4. Apply only the exact reviewed digest.
5. Run the generated read-only check and relevant project-owned validation.
6. Retain the transaction receipt for exact rollback while postimages remain
   unchanged.
7. Assess long-running-work applicability separately. Absence never means
   `not_applicable`.

Existing tasks, evidence, decisions, focus, workflow adoption, permissions,
and project facts must be preserved unless their exact project-owned change is
separately reviewed. Structural migration does not establish harness adoption,
package adoption, release readiness, or project readiness.
