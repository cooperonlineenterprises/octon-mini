# Migration: 0.2.0 to 1.0.0

This is a breaking blueprint migration. A generated project is an independent
snapshot; do not copy 1.0.0 files over an adopted 0.2.0 harness or dossier.

## Contract changes

- seven kernel files and current state move from `.yaml` to strict `.json`;
- standard dossier registries move into `project-dossier/machine-readable/`
  as strict JSON;
- dossier IDs move from three to four numeric digits;
- artifact catalog and path-authority mirrors become generated and validated;
- shared schemas are copied to `.agent/schemas/`;
- new-project generation requires a nonexistent or empty directory and uses a
  staged transaction;
- existing-project work starts with `plan_adoption.py`;
- the runtime floor is Python 3.11;
- lifecycle transitions, global references, nested `AGENTS.md`, extensions,
  whole-repository freshness, manifests, and checksums fail closed;
- high-assurance refresh assigns one generation ID across its derived set.

## Migration procedure

1. Run the 1.0.0 adoption planner against the project and preserve its output
   as migration evidence.
2. Read all target-project instructions and locate accepted decisions,
   authority sources, active tasks, current-state claims, and real validation
   commands.
3. Map each 0.2.0 file to the 1.0.0 concern; identify functional equivalents
   instead of assuming a missing pathname is a gap.
4. Convert structured sources with a parser that rejects duplicate keys.
   Preserve stable meaning and record every ID mapping.
5. Allocate four-digit successors where an old identifier cannot be preserved
   unambiguously. Never silently reuse an ID.
6. Keep accepted project decisions immutable; use successor decisions when
   the migration changes meaning.
7. Generate or rebuild the artifact catalog and path-authority mirror from one
   source; do not edit both.
8. Register domain rules as restrictions-only extensions. Record pinned
   dependencies for any non-JSON format.
9. Configure actual project checks and named fingerprint exclusions with a
   reason. Default to the whole repository.
10. Run read-only validation and adversarial tests. For high assurance, run
    refresh and then the final read-only check.
11. Record the exact migrated revision, remaining unknowns, skipped checks,
    external effects, rollback path, and resumption point.

## Rollback

Retain the pre-migration revision and its historical dossier as explicitly
noncurrent evidence. Rollback restores that exact revision; it must not merge
old YAML and new JSON kernels into a dual-authority state.

## Completion gate

Migration is complete only when no legacy kernel pathname remains live, every
record reference resolves, the exact target revision passes its project and
blueprint checks, and an unfamiliar maintainer can resume from the handoff.
Structural completion does not establish project readiness.
