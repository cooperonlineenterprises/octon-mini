# Migration: 1.0.0 to 1.0.1

This patch corrects release-blocking lifecycle and validation behavior while
preserving the stable domain-neutral kernel and `harness.extension.v1`.
Generated project snapshots never upgrade automatically.

## Who should migrate

Migrate a generated `1.0.0` project when it needs supported derivative refresh,
project-local dossier evolution, hardened validator guarantees, or any
high-assurance control corrected by `1.0.1`. A project may remain on `1.0.0`
temporarily only if it records that decision, the known limitations, and an
owner-approved review date.

## Authority boundary

Do not copy `1.0.1` files over an active project. Read the target repository's
instructions first, inventory its accepted authority and records, and use a
project-specific migration change. Blueprint defaults cannot supersede project
decisions, permissions, approvals, or facts.

## Required sequence

1. Run the `1.0.1` adoption planner read-only and save its output as migration
   evidence.
2. Map current project paths and functional equivalents to the `1.0.1`
   contracts; resolve every collision explicitly.
3. Inventory the exact `1.0.1` governed paths required by the selected
   profile. Add the new local schemas and stores deliberately, disposition
   unknown live-governance paths, and leave conditional High-Assurance records
   unassessed until their triggers are decided.
4. Introduce the project-local dossier artifact registry and populate it from
   accepted project artifacts. Do not infer authority from a file's location.
5. Replace independently edited dossier catalog, path-authority, and manifest
   data with outputs generated transactionally from the registry and current
   project tree.
6. Reconcile schema and validator changes, including lifecycle, references,
   gates, supersession, extension restrictions, path confinement, and
   read-only checks.
7. Migrate `.agent/state/current.json` to the closed project-maintained
   resumption schema. Reconcile project and harness adoption status; resolve
   active-task, accepted-decision, current-evidence, external-authority, and
   adoption-decision references. Keep adoption-decision references null until
   adoption is accepted.
8. For High Assurance, migrate agent and workflow records and move reusable
   skill version and trust metadata from `SKILL.md` frontmatter into
   `references/provenance.json`. Adopt a capability only with assigned
   ownership, completed trust reviews, exact included files, pinned imported
   version and fingerprint, and an accepted externally authoritative adoption
   decision. Adopted workflows may depend only on adopted agents, which may
   depend only on adopted skills.
9. Reassess every completed task, final artifact, readiness gate, waiver, and
   approval. Evidence must be passing, fresh, subject- or task-bound, and
   resolvable. Approval attestations must identify the principal, immutable
   evidence fingerprint, validity window, external authority source, and
   current revocation or supersession state.
10. For High Assurance, evaluate whether approval, coordination, recovery,
   evaluation, or metric triggers apply and adopt only the justified records.
11. Refresh all derived outputs, run the target's own checks, and run the
   `1.0.1` conformance and mutation suites. Regenerate rather than hand-edit
   validation reports, verify every reported check was executed, and record
   failures, skipped checks, limitations, dirty/untracked/ignored scope, and
   external effects without making a readiness inference.
12. Update `.project-blueprint-origin.json` only through the authorized
   migration process, preserving the original generation provenance and
   recording the migration event.
13. Obtain any project-required review or approval before treating the
   migration as accepted.

## Verification

Migration is complete only when:

- `python -B .agent/scripts/refresh.py --refresh` completes transactionally;
- the immediately following `python -B .agent/scripts/validate.py --check`
  reports no stale derivatives and passes;
- record IDs and references are unique and resolvable;
- the exact required governed-file inventory matches the selected profile;
- current-state and adoption statuses and references are coherent;
- adopted capability provenance, adoption decisions, and dependency chains
  validate;
- closure, gate, waiver, and approval evidence semantics validate;
- every registered dossier path is repository-confined and has one declared
  authority class;
- no extension can loosen core restrictions, and post-execution repository
  mutation detection passes; preventing transient or out-of-repository writes
  still requires an external confinement boundary;
- generated validation evidence describes only checks actually run and
  discloses scope, failures, skips, limitations, dirty state, and external
  effects; and
- the handoff names the accepted version, remaining limitations, and a safe
  resumption point.

If a target cannot meet these conditions, keep the migration explicitly
in-progress or roll back the project-specific migration through its normal
change-control mechanism. Do not claim `1.0.1` conformance.
