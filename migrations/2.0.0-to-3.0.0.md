# Migration: 2.0.0 to 3.0.0

This is a breaking blueprint and harness-kernel migration. Version `3.0.0`
adds an evidence-backed, non-authorizing collaboration assessment and a closed,
provider-neutral Git workflow portfolio for one to five write-capable humans.
Generated projects remain independent snapshots and never upgrade
automatically.

## Contract changes

- `harness.project.v3` adds the required closed
  `harness.collaboration-profile.v1` record. Its generated baseline contains no
  people, hosted facts, recommendation, decision, or permission.
- `harness.tools.v2` replaces vague Git actions with exact operation records,
  effects, authority classes, workflow eligibility, and safeguards. Unknown
  operations fail closed; composite `pull` and raw `force_push` are prohibited.
- `harness.validators.v3` adds the read-only
  `--assess-collaboration` report and semantic collaboration/workflow checks.
- `harness.git-workflows.v1` defines only `solo_direct`, `solo_hybrid`,
  `pair_pr`, `tiny_pr`, and the `concurrent_work` modifier. More than five
  write-capable humans is explicitly unsupported and has no enterprise
  fallback.
- Every profile gains `.agent/workflows/small-team-git.json`, its provider-
  neutral guidance, an inactive GitHub adapter guide, and a pull-request record
  template. GitHub remains optional.
- Profile selection remains risk-based. Team size selects only a base
  collaboration workflow; risk, external effects, and assurance remain
  independent axes.

## Authority and information boundary

Do not infer collaborators from activity alone, count bots or read-only users
as developers, or treat a recommendation as adoption. A collaborator count,
workflow record, installed tool, branch, PR, review, CI result, or hosted
setting creates no permission. Workflow adoption requires a project-owned
accepted decision and still does not authorize publication or other external
effects.

The legacy v2 Git vocabulary is too vague to translate when it was modified or
separately adopted. The reference reconciler accepts only the exact canonical
v2 tools and validators plus an explicit project-owned classification that the
legacy Git policy remained an unadopted baseline. Any divergent, adopted,
ambiguous, or mixed live policy fails for project-specific reconciliation.

## Required sequence

1. Read the target repository instructions and preserve unrelated work,
   accepted authority, stable IDs, active records, and the exact v2 revision.
2. Run the 3.0.0 adoption planner read-only and record collisions and
   functional-equivalent candidates without accepting them automatically.
3. Classify the existing v2 Git policy. If it was changed, interpreted as
   standing permission, or separately adopted, stop the mechanical path and
   reconcile every operation through a project-owned migration task.
4. Preserve the whole-harness adoption state and decision separately. Add the
   new collaboration profile as `not_assessed`; do not carry harness adoption
   into workflow adoption.
5. Gather aggregate, privacy-minimized project observations. Keep declared
   maintainers, hosted write access, recent activity, review capacity,
   concurrency, and external contribution mode distinct. Record evidence and
   freshness without unnecessary identities.
6. Run `--assess-collaboration` read-only. Resolve unknown, stale, and
   conflicting signals before recording a recommendation. More than five
   write-capable humans remains outside supported scope.
7. Select one integration method and, if adopting a workflow, link a new or
   existing accepted project-owned decision. Do not infer reviewers, branch
   protection, required checks, providers, credentials, or hosted settings.
8. Reconcile local Git and optional hosted-change operations to the new
   `harness.tools.v2` exact catalog. Keep fetch separate from explicit
   integration; retain separate release authority and the
   force-with-lease/default-branch safeguards.
9. Add all new required schemas, workflow files, guidance, and origin inventory
   entries. Regenerate only derived outputs.
10. Run the read-only check, collaboration report, generated mutation suite,
    refresh, and authorized project checks on the exact migrated revision.
11. Append the migration event to `.project-blueprint-origin.json` through the
    project’s authorized mechanism while preserving `initial_generation`.

## Executable reference fixtures

The closed reference reconciler validates a representative v2 bundle and
retains exact rollback evidence:

```text
python3 -B skills/project-bootstrap/scripts/test_migration_2_0_0_to_3_0_0.py
python3 -B skills/project-bootstrap/scripts/migrate_2_0_0_to_3_0_0.py \
  --input skills/project-bootstrap/fixtures/migrations/2.0.0-to-3.0.0/valid/v2-minimal.json \
  --check
```

To materialize the reference result, pass `--output` with a new path. The tool
refuses in-place and existing-path output, performs no network access, runs no
project command, and never infers or adopts a workflow. It is not a general
live-project upgrader.

## Verification

Migration is complete only when:

- project, tools, validators, workflow, and origin records validate against
  the v3 schemas and exact controlled vocabularies;
- collaboration begins unknown unless current project-owned evidence was
  deliberately assessed outside the reference transform;
- unknown, stale, conflicting, zero-writer, and over-five states fail safely;
- bots, automation, read-only collaborators, and activity do not inflate or
  erase write-capable-human authority;
- reviewer requirements never exceed one or established capacity;
- every supported workflow operation resolves, while prohibited/destructive
  operations are absent from normal steps;
- team size has not changed the selected assurance profile or granted
  permission;
- no GitHub identity, reviewer, protection, required check, credential,
  provider, release, or passing-CI fact was fabricated;
- ordinary `--check` and `--assess-collaboration` remain read-only and
  network-free;
- the previous migration suites still pass; and
- a second reference migration application is an exact no-op while every
  fail-closed fixture is rejected.

## Rollback

Retain the exact pre-migration bytes, digest, and parsed v2 live state as
noncurrent evidence. Rollback remains a separately authorized project action
and restores the v2 project, tool, validator, workflow absence, and origin
contracts together. Never mix live v2 and v3 authority. Rollback evidence
inherits the source bundle’s sensitivity, access, and retention requirements.
